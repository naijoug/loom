# Loom MVP 实施计划

- **日期**：2026-05-09
- **作者**：Codex
- **状态**：已定稿（可实施）
- **最近更新**：2026-05-09 决策固化技术栈与流程关键问题

## 目标

实现一个最小可用的 Tauri 桌面端 MVP：能够打开本地项目、配置多个 Agent 命令、发起多 Agent 需求规划讨论、选择一个主 Agent 执行实施、让至少一个 Review Agent 参与审查、启动本地调试或验证命令、实时展示日志、接收人工反馈，并驱动“修复 -> 验证”的循环，直到任务完成或明确阻塞。

这个 MVP 优先验证完整开发闭环，而不是追求插件市场、复杂自动化或高级协作能力。

## 非目标

- 不实现完整插件市场或远程 Agent 注册中心。
- 不实现云端同步、团队账号或多人协作。
- 不实现完整生产级沙箱，只做可见命令执行和基础权限策略。
- 不把浏览器自动化或 GUI 视觉测试作为 MVP 必选能力。
- 不追求对所有语言和框架的完美项目识别。
- 不做复杂 Prompt 评测、模型对比或 Agent 质量评分。
- 不把 Git 提交编排作为 MVP 必选能力。

## 成功标准

- 用户可以启动 Tauri 应用并打开一个本地项目目录。
- 用户可以配置至少 3 个 Agent 命令，例如 Codex、Claude Code、Hermes 或 OpenClaw。
- 应用可以在规划阶段运行选定 Agent，并把输出保存到同一个任务记录中。
- 应用可以生成或展示一份汇总后的最终计划。
- 用户可以选择一个主 Agent 和至少一个 Review Agent。
- 应用可以把最终计划作为上下文传给主 Agent，并在指定项目中执行。
- 应用可以调用 Review Agent，并展示阻塞问题、修改建议和可接受风险。
- 应用可以启动配置好的调试或验证命令，实时展示 stdout/stderr，并保存命令元数据。
- 应用可以识别命令失败，并从日志中提取基础错误摘要。
- 用户可以在调试过程中提交人工反馈，并绑定到当前任务运行记录。
- 同一个任务记录中可以完成至少两轮 `调试 -> 修复 -> 验证`。
- 应用可以展示或导出最终任务总结，包含修改文件、验证结果和剩余风险。

## 已固化技术栈（MVP 阶段不再讨论）

- 桌面端外壳：**Tauri 2.x**（使用 `@tauri-apps/cli` v2 系列模板）。
- 前端：**TypeScript + React 18 + Vite**。
- 包管理器：**pnpm**（锁定 `pnpm-lock.yaml`，CI 与本地一致）。
- 后端：Rust Tauri commands，异步运行时使用 `tokio`。
- 持久化：
  - 全局配置（Agent、最近项目、应用偏好）放 **应用数据目录** 下的 JSON 文件（通过 Tauri `path::app_data_dir`）。
  - 单个项目的任务记录、日志、计划文档放项目根目录下的 **`.loom/`** 子目录（默认加入 `.gitignore` 提示）。
- Agent 集成：优先实现命令行适配器；MVP 默认内置一个 **dummy adapter**（确定性输出，便于本地测试和 CI），协议字段预留 MCP / HTTP 适配器扩展空间。
- 日志传输：Rust 读取子进程输出，通过 Tauri `emit` 结构化事件推送前端；前端用环形缓冲 + 虚拟滚动渲染，避免长日志阻塞。
- Git 依赖：MVP 假设项目使用 Git；非 Git 项目降级为"仅展示文件 mtime 列表"，不阻塞流程。

脚手架实现前，需要按 Tauri 2.x 官方模板验证 `create-tauri-app` 命令和目录结构。

## 建议任务状态机

```text
drafting_requirements
  -> planning
  -> plan_review
  -> ready_to_implement
  -> implementing
  -> reviewing
  -> debugging
  -> fixing
  -> verifying
  -> debugging
  -> completed | blocked | cancelled
```

每次状态流转都应写入任务历史，包含时间、执行者、输入摘要、输出摘要，以及可用的验证证据。

## 风险

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| 不同 Agent CLI 的交互方式不兼容 | 高 | 高 | 先支持命令行适配器、stdin prompt 和 prompt 文件模式；必要时再补伪终端支持 |
| 长时间进程日志阻塞 UI | 中 | 高 | Rust 通过事件流推送日志，持久化异步且有边界 |
| 自动修复执行不安全命令 | 中 | 高 | MVP 展示明确命令上下文并保存能力标记，高风险操作受策略限制 |
| 项目检测不完整 | 高 | 中 | 支持手动命令覆盖，分析器只做启发式并展示判断依据 |
| Tauri 前后端边界变模糊 | 中 | 中 | 进程、文件系统、持久化放 Rust；流程展示和用户交互放前端 |
| Review 输出难以可靠分类 | 中 | 中 | 保存原始 Review 输出，先做简单分类并允许用户调整 |
| 多 Agent 并发输出造成理解混乱 | 中 | 中 | MVP 只在规划阶段安全并发，实施和调试阶段默认串行 |

## 验证策略

- 逐里程碑验证：
  - M1：应用能启动，前端能调用 Rust 命令。
  - M2：项目路径、分析结果和 Agent 配置重启后仍存在。
  - M3：规划 Agent 能运行，输出能保存到同一任务。
  - M4：主 Agent 实施运行和 Review Agent 运行能被记录。
  - M5：调试命令能运行、日志能实时展示、失败摘要能捕获。
  - M6：反馈和日志能触发修复 Agent 运行，并重新验证。
  - M7：完整场景能生成最终总结。

- MVP 端到端验收场景：
  1. 打开样例项目。
  2. 配置三个 dummy 或真实 Agent 命令。
  3. 从需求文本创建任务。
  4. 运行两个规划 Agent。
  5. 保存最终计划。
  6. 选择主 Agent 和一个 Review Agent。
  7. 运行实施。
  8. 运行 Review。
  9. 启动失败的验证命令。
  10. 捕获日志错误摘要。
  11. 添加人工反馈。
  12. 运行修复。
  13. 重新运行验证。
  14. 再重复一轮修复/验证。
  15. 标记完成并生成总结。

- 回滚策略：
  - 每个里程碑保持可独立合入。
  - 如果进程管理不稳定，先禁用自动修复，保留手动调试命令执行。
  - 如果 Agent 调用不可靠，先交付确定性的 dummy adapter 和一个稳定 CLI adapter。

## 验收门槛

MVP 不能只停留在界面演示。完成时，一个任务记录必须能展示（前提：用户已在配置中保存了至少 3 个 Agent，但单个任务只需调用其中 2 个参与规划）：

- 原始需求；
- 至少两个规划 Agent 输出（来自已配置的 3 个 Agent 中任选 2 个）；
- 最终计划；
- 主 Agent 实施运行；
- Review Agent 结果；
- 至少一次调试命令运行；
- 至少一次错误摘要；
- 一条人工反馈；
- 两轮修复/验证；
- 最终完成或阻塞总结。
