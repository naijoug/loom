**假设**(均为推断,无项目证据):① 本机 4–8 核桌面机,工具为 API 型 CLI(网络/IO 为主);② 各工具回答相互独立,无共享写冲突;③ 目标是低延迟与稳定,而非最大吞吐。

**并行 vs 串行**
- 并行:整轮延迟≈最慢者,吞吐高;代价是[REDACTED sensitive line] 突发、速率限制风险、输出交错难归因。
- 串行:轮间可见前序结论(便于反驳/收敛)、失败隔离最好;代价是延迟累加,独立子问题被无谓排队。

**建议**:轮内并行、轮间串行(barrier 汇总)。并发上界取 `min(工具数, 3)`,留 1 核给 UI 与汇总;若发现是本地模型(CPU 主导)降到 2。

**部分失败策略**:fail-open——单个工具失败或超时(建议 ~120s)不取消整轮;记录失败原因,允许有界重试一次(短退避);仍失败则在汇总中标记“缺失”并降权,不阻塞其余结论。仅当 ≥半数工具失败才判整轮无效。

**风险**:若各工具共享速率配额,并发 3 可能触发限流;CLI 崩溃语义(退出码非零 vs 挂起)需分别设超时与失败判定。
