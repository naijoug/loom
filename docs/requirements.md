## 历史交付范围（2026-09-20）

当前优先交付可靠的单 Agent Chat：选项目 → 检测本机 Agent → 会话 → 流式回复 → 停止 → 续聊。至少一个真实 CLI 完整通过验收即可；次级 Agent 可选，不以四阶段任务闭环为 Chat 前提。

ChatSession 与 Task 分离。本文第 1–9 节保留长期产品方向和高级 Task 工作流；第 10–11 节是其独立范围与验收，不覆盖本节的 Chat 交付顺序。产品范围以本文为准，[当前重构计划](plans/2026-09-17/10:15-local-agent-chat-rebuild.md) 细化实施安排；历史计划只作背景。

Chat 成功标准：

- 至少一个真实本机 Agent 支持流式回答、连续三轮追问、停止后再发和重启续聊，并保留真实验收记录。
- 同会话仅一个活动回合，切换项目/会话不串流；非零退出、超时、停止和中断可识别，不用模拟结果掩盖故障。
- 会话和已保存输出重启后可读；Chat 不隐式创建或推进 Task。
- 当前权限值为 `explore` / `ask` / `auto`；`ask` 表示 Composer 每回合授权可写 CLI，不表示逐工具审批。CLI 实际能力和限制见 [Chat 契约](architecture/chat-contracts.md)。
- 新建与续聊的有效权限需一致；未经真实验证的只读/审批能力不能宣称已保证。逐工具审批须有已验收的双向协议，不能通过改名现有 Ask 交付。
- 原生续聊发送新增输入；无原生续聊时重放有预算的历史并标记截断，不静默丢弃最新请求。
- 桌面端真实验证通过后才可宣称 Chat 完成，具体矩阵见 [测试指南](testing.md)。

当前实现与未完成目标分别列于 [Chat 契约](architecture/chat-contracts.md)，计划或本文成功标准不是已实现证明。

## 1. 背景

本项目目标是实现一个面向软件开发任务的桌面端编程助手。它不是单一 Agent 的聊天壳，而是一个能够统一调度多种本地或远程 Agent 工具的开发工作台，例如 Codex、Claude Code、OpenClaw、Hermes 等。

用户可以围绕一个开发目标组织多 Agent 讨论方案、选择主 Agent 执行、让其它 Agent 参与 Review，并在调试验收阶段通过自动或人工介入方式形成“实施 -> 调试 -> 修复 -> 再验收”的闭环。

## 2. 长期产品目标

- 统一接入用户已安装的多种 Agent 工具。
- 支持多 Agent 针对同一需求生成、讨论、比较和完善计划文档。
- 支持选择一个主 Agent 负责实施，其它 Agent 负责审查、补充和验证。
- 支持本地项目调试：启动开发命令、观察日志、识别错误、提出或执行修复。
- 支持自动验收和人工介入验收两种模式。
- 支持任务循环推进，直到完成或明确阻塞。

## 3. 目标用户

- 需要长期使用多个 AI 编程工具的开发者。
- 希望把需求讨论、代码实施、Review、调试验收集中到一个桌面端流程中的个人开发者或小团队。
- 需要保留执行日志、决策过程、计划文档和验收记录的项目维护者。

## 4. 核心概念

### 4.1 Agent 工具

Agent 工具指用户本机已经安装或可以通过命令行调用的 AI 编程助手，包括但不限于：

- Codex
- Claude Code
- OpenClaw
- Hermes
- 其它兼容命令行或插件协议的 Agent

每个 Agent 需要配置：

- 名称
- 可执行命令
- 工作目录策略
- 支持的能力标签，例如规划、编码、Review、调试、测试、文档
- 输入输出协议，例如纯命令行、JSON、MCP、插件 API
- 是否允许修改文件
- 是否允许执行命令

### 4.2 任务

任务是一次完整的开发目标，包含：

- 原始需求
- 讨论记录
- 计划文档
- 选定的主 Agent
- 参与 Review 的 Agent
- 执行日志
- 调试日志
- 修复循环记录
- 最终验收结果

### 4.3 主 Agent 与协作 Agent

- 主 Agent：负责主要实现、文件修改、测试执行和修复。
- 协作 Agent：负责方案补充、代码 Review、风险识别、测试建议、验收意见。

同一任务中主 Agent 可以切换，但需要记录切换原因。

## 5. 高级 Task 工作流程

### 5.1 第一步：需求讨论与计划完善

用户输入开发目标后，系统进入需求讨论阶段。

功能要求：

- 用户可以选择参与讨论的 Agent。
- 每个 Agent 基于同一需求输出自己的计划文档或分析意见。
- 系统汇总不同 Agent 的计划，提取共识、冲突点、风险和待确认问题。
- 用户可以继续补充需求，要求 Agent 重新讨论或修订计划。
- 系统产出最终实施计划，作为后续实施阶段的输入。

计划文档至少包含：

- 目标与非目标
- 用户场景
- 功能拆解
- 技术方案
- 文件或模块影响范围
- 测试策略
- 风险与回滚方案
- 验收标准

### 5.2 第二步：实施与 Review

用户确认计划后，进入实施阶段。

功能要求：

- 用户选择一个主 Agent 执行实施。
- 系统将最终计划、仓库上下文和约束传给主 Agent。
- 主 Agent 可以修改代码、运行命令、提交阶段性结果。
- 其它 Agent 可以在关键节点进行 Review。
- Review 结果需要分类展示：阻塞问题、建议修改、可接受风险。
- 主 Agent 根据 Review 意见继续修改，直到达到进入调试验收阶段的条件。

实施阶段需要记录：

- 执行的命令
- 修改的文件
- Agent 输出摘要
- Review 意见
- 已采纳与未采纳的建议
- 当前任务状态

### 5.3 第三步：调试验收

调试验收阶段分为自动模式和人工介入模式。

#### 5.3.1 自动模式

系统需要尽量自动识别项目如何启动和验证。

功能要求：

- 分析项目类型，例如 Node.js、Python、Rust、Go、Electron、Tauri、Flutter 等。
- 自动识别常用命令，例如安装依赖、启动本地开发服务、运行测试、类型检查、Lint。
- 启动本地调试命令并实时展示日志。
- 解析日志中的错误、警告、端口、URL、测试失败信息。
- 遇到错误时，自动交给主 Agent 分析并修复。
- 修复后重新启动或重新运行验证命令。
- 形成“发现问题 -> 修复 -> 再验证”的自动循环。

自动模式需要有安全边界：

- 删除文件、重置 Git、安装新依赖、访问外部生产服务等高风险行为需要明确策略。
- 命令执行需要展示命令内容、工作目录和退出状态。
- 长时间运行的命令需要支持停止、重启和查看历史日志。

#### 5.3.2 人工介入模式

人工介入模式允许用户在调试过程中指出问题，帮助 Agent 定位。

功能要求：

- 系统启动本地调试并实时展示日志。
- 用户可以输入观察到的问题，例如页面空白、按钮无响应、接口 500、样式异常。
- 用户可以附加截图、日志片段、复现步骤或期望行为。
- 系统将用户反馈、当前日志和项目上下文传给主 Agent。
- 主 Agent 基于反馈定位并修复问题。
- 修复后系统继续调试验收。

人工介入内容需要进入任务记录，作为后续 Review 和验收依据。

### 5.4 第四步：修复与验收循环

系统需要支持持续循环：

1. 启动或运行验证。
2. 收集日志、测试结果和用户反馈。
3. 判断是否通过验收。
4. 如果失败，生成问题摘要。
5. 主 Agent 修复。
6. 协作 Agent Review。
7. 重新验证。
8. 直到任务完成、用户停止或遇到不可恢复阻塞。

循环结束时需要生成任务总结：

- 完成的需求
- 修改的文件
- 关键决策
- 测试与验证结果
- 剩余风险
- 后续建议

## 6. 功能需求

### 6.1 Agent 管理

- 添加、编辑、删除 Agent 配置。
- 检测 Agent 命令是否可用。
- 展示 Agent 支持能力和当前状态。
- 支持为不同阶段设置默认 Agent。
- 支持禁用某个 Agent 的文件写入或命令执行权限。

### 6.2 项目管理

- 打开本地项目目录。
- 识别项目类型和技术栈。
- 展示项目基本信息、Git 状态、可用脚本和常见命令。
- 保存每个项目的 Agent 偏好和运行配置。

### 6.3 任务管理

- 创建开发任务。
- 保存任务状态和历史记录。
- 支持任务暂停、恢复和终止。
- 支持查看每轮计划、实施、Review、调试、修复记录。
- 支持导出任务总结。

### 6.4 多 Agent 讨论

- 并行调用多个 Agent 输出计划。
- 汇总多份计划文档。
- 标记共识、冲突、风险和问题。
- 支持用户基于汇总结果继续追问或修订需求。
- 生成最终计划文档。

### 6.5 实施控制

- 选择主 Agent。
- 指定协作 Review Agent。
- 展示实施进度和文件变更摘要。
- 支持查看实时输出。
- 支持中断、重试、切换 Agent。

### 6.6 调试与日志

- 支持启动长时间运行的开发服务。
- 实时采集 stdout、stderr 和退出码。
- 自动识别 URL、端口、错误堆栈、测试失败。
- 支持日志搜索、过滤和折叠。
- 支持把日志片段发送给 Agent 分析。

### 6.7 自动修复

- 根据日志或测试失败生成问题摘要。
- 调用主 Agent 修复。
- 运行最小必要验证。
- 修复失败时升级给其它 Agent Review。
- 记录每次修复尝试和结果。

### 6.8 人工介入

- 用户可以随时输入问题描述。
- 支持附加复现步骤、截图和日志片段。
- 支持把用户反馈绑定到某次调试会话。
- Agent 修复后，需要展示修复说明和验证证据。

## 7. 非功能需求

### 7.1 可扩展性

- Agent 接入层应抽象为适配器。
- 新 Agent 不应要求修改核心流程。
- 命令行、MCP、HTTP API、插件协议可以作为不同适配器类型。

### 7.2 安全性

- 所有命令执行需要可追踪。
- 高风险命令需要策略限制。
- 凭据、Token、环境变量不应写入任务日志。
- Agent 输出中的敏感信息需要支持脱敏。

### 7.3 稳定性

- 长任务需要可恢复。
- 桌面端重启后应能恢复任务状态。
- Agent 进程异常退出时需要记录原因。
- 日志采集不能阻塞 UI。

### 7.4 可观测性

- 每个阶段需要有明确状态。
- 每次 Agent 调用需要有输入摘要、输出摘要、耗时和退出状态。
- 每个命令需要记录工作目录、命令、开始时间、结束时间和退出码。

### 7.5 用户体验

- 主流程应围绕四个阶段组织：需求讨论、实施 Review、调试验收、修复循环。
- 用户可以随时查看“当前系统正在做什么”。
- 自动模式下需要展示当前判断依据。
- 人工模式下需要方便用户快速补充问题和证据。

## 8. 建议信息架构

桌面端主界面建议包含：

- 项目侧边栏：项目、任务、Agent 配置。
- 任务流程区：四阶段进度、当前状态、下一步动作。
- 讨论与计划区：多 Agent 计划、汇总、最终计划。
- 实施区：主 Agent 输出、文件变更、Review 结果。
- 调试区：命令、日志、端口、错误摘要。
- 人工反馈区：问题描述、复现步骤、截图或日志片段。
- 总结区：完成情况、验证证据、剩余风险。

## 9. 建议技术架构

### 9.1 桌面端外壳

桌面端外壳确定采用 Tauri。

选择理由：

- Tauri 更轻量，适合长期运行的开发工作台。
- Tauri 基于 Rust 后端，适合实现本地命令执行、进程管理、日志采集和文件系统访问。
- 前端仍可使用 Web 技术实现复杂交互界面。
- 相比 Electron，Tauri 的应用体积和资源占用更适合多 Agent 并发、日志流和长任务场景。

该决策意味着核心本地能力应优先放在 Tauri command / Rust sidecar / Rust service 中实现，前端负责流程编排展示、交互和状态可视化。

### 9.2 核心模块

- UI 层：任务流程、日志、配置、人工反馈。
- Orchestrator：任务状态机、多 Agent 调度、阶段推进。
- Agent Adapter：不同 Agent 工具的调用适配。
- Command Runner：命令执行、日志采集、进程生命周期管理。
- Project Analyzer：项目类型识别、脚本发现、验证命令推断。
- Review Engine：组织协作 Agent Review。
- Persistence：任务、日志、配置、计划文档持久化。

### 9.3 状态机

建议任务状态：

- `drafting_requirements`
- `planning`
- `plan_review`
- `ready_to_implement`
- `implementing`
- `reviewing`
- `debugging`
- `fixing`
- `verifying`
- `completed`
- `blocked`
- `cancelled`

## 10. 高级 Task 工作流范围（原完整闭环 MVP）

本节描述高级 Task 的完整闭环，独立于当前 Chat 交付。

高级 Task 闭环包含：

- 本地项目打开。
- Agent 命令配置。
- 多 Agent 计划讨论。
- 最终计划文档生成。
- 选择主 Agent 实施。
- 至少一个协作 Agent Review。
- 命令行调试启动。
- 实时日志展示。
- 日志错误摘要。
- 自动修复循环。
- 人工问题输入。
- 任务总结。

本阶段暂不强制包含：

- 完整插件市场。
- 复杂权限沙箱。
- 团队多人协作。
- 云端同步。
- 可视化测试录制。
- 完整 GUI 自动操作。

## 11. 高级 Task 工作流验收标准

### 11.1 Agent 接入

- 用户可以配置至少 3 个 Agent 命令。
- 系统可以检测命令是否可执行。
- 系统可以向 Agent 发送任务上下文并获得输出。

### 11.2 计划阶段

- 同一需求可以触发多个 Agent 生成计划。
- 系统可以生成一份汇总计划。
- 用户可以确认汇总计划并进入实施。

### 11.3 实施阶段

- 用户可以选择主 Agent。
- 主 Agent 可以在指定项目目录中实施修改。
- 协作 Agent 可以对修改进行 Review。
- Review 结果能被记录并展示。

### 11.4 调试验收阶段

- 系统可以启动用户配置的开发命令。
- 系统可以实时展示日志。
- 系统可以识别命令失败和日志中的错误。
- 系统可以把错误交给 Agent 修复。
- 修复后系统可以重新运行验证。

### 11.5 人工介入

- 用户可以在调试过程中输入问题描述。
- 系统可以将用户描述和当前日志一起交给 Agent。
- 修复结果需要有验证记录。

### 11.6 完成闭环

- 一个任务可以经历至少两轮“调试 -> 修复 -> 验收”循环。
- 任务完成后生成总结。
- 总结中包含修改范围、验证结果和剩余风险。

## 12. 风险与待决策事项

- 不同 Agent 的输入输出协议差异较大，需要设计稳定的适配器接口。
- 部分 Agent 可能不支持非交互式调用，需要伪终端或会话管理。
- 自动修复可能执行高风险命令，需要权限策略。
- 日志解析不能完全依赖固定正则，需要结合项目上下文和 Agent 分析。
- Tauri 前后端边界需要进一步明确，尤其是 Agent 进程管理、日志流和权限控制应该放在哪一层。
- 是否内置浏览器自动验收能力，需要根据目标技术栈决定。
